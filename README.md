# NAVGUARD

AI-Assisted GNSS-Denied Mobile Navigation & Sensor Fusion System.

NAVGUARD is an Android-based research and development project focused on pedestrian navigation continuity using smartphone sensors and on-device processing.

Stage 4 — Baseline PDR is implemented, statically validated across six implementation/test paths, and physically verified for its defined diagnostic scope. It causally associates each accepted `TYPE_STEP_DETECTOR` event with the latest valid `TYPE_ROTATION_VECTOR` true-north-corrected handset heading at or before the step's `SensorEvent.timestamp`; future headings and interpolation are prohibited. A fixed, uncalibrated, unvalidated 0.75 m research baseline produces horizontal local ENU displacement using `ΔE = L × sin(ψ)` and `ΔN = L × cos(ψ)`. `flutter analyze --no-pub`, all 118/118 tests, the debug APK build, and `git diff --check` passed.

Physical verification on the Xiaomi Redmi Note 9 Pro included a stationary 30-second session with zero accepted/integrated steps; two manually counted 20-step straight walks with 20 associated/integrated steps each; an intended 20-step L-shaped walk with 22 detected/associated events; an independent corrected north check; and explicit `baseline_pdr_cancelled` cancellation. The initial absolute-direction concern was resolved when the user determined that the first walking reference direction had been chosen incorrectly; no Stage 4 heading-axis defect was established. These observations verify the defined runtime flow, causal association, local-ENU integration, and cancellation, but do not validate PDR, step-detection, step-length, heading, true-north, or physical-distance accuracy.

Stage 5 — ARCore Relative Motion → ENU Foundation is implemented, statically validated across six implementation/test paths, and physically verified for its defined diagnostic scope. It uses `Frame.getAndroidSensorPose()` in the Android sensor frame (+X right, +Y physical top edge, +Z outward from the screen), creates a local runtime ARCore anchor after a 2-second stationary-assumed alignment, and computes `anchor.pose.inverse().compose(currentAndroidSensorPose)`. The frozen initial device-to-true-ENU rotation uses `TYPE_ROTATION_VECTOR` plus `android.hardware.GeomagneticField` declination. The formal movement window is 30 seconds. `SensorEvent.timestamp` and `Frame.getTimestamp()` remain separate authorities; no numeric cross-clock comparison is performed. `flutter analyze --no-pub`, all 141/141 tests, the debug APK build, and `git diff --check` passed.

Stage 6 — Evaluation Mode + Ground Truth Firewall is implemented, statically validated across six implementation/test paths, and physically verified for its defined evaluation-isolation scope. Physical `GPS_PROVIDER` data remains active only as `protected_ground_truth_only`; Config A is a software-defined denied estimator whose API receives only `TYPE_STEP_DETECTOR` steps and true-north-corrected `TYPE_ROTATION_VECTOR` handset heading. Its fixed, uncalibrated, unvalidated 0.75 m model remains `ΔE = 0.75 × sin(ψ)` and `ΔN = 0.75 × cos(ψ)`. Step and heading use nanosecond `SensorEvent.timestamp`; protected GNSS uses `Location.getElapsedRealtimeNanos`; and the operation window uses `SystemClock.elapsedRealtimeNanos`. The comparator selects the latest finalized estimator state at or before each protected-GT timestamp without interpolation or correction. `flutter analyze --no-pub`, all 169/169 tests, the debug APK build, and `git diff --check` passed.

The stationary Stage 6 session accepted and matched 30/30 protected-GT fixes, accepted zero steps, remained at `E = 0, N = 0`, and had a final pre-correction error of approximately 0.506 m. The initial moving session correctly exposed an implementation defect: 11 accepted steps were all unassociated despite 1,531 valid heading samples. Stage 6 had retained only the latest delivered heading; callback timing could make that sample newer than a delayed step while discarding older causal headings. The fix mirrors Stage 4 by buffering valid headings and accepted step timestamps, then selecting the greatest heading timestamp satisfying `T_heading <= T_step`. In the post-fix walk, the user manually counted 20 physical steps; 16 step updates were observed, five were outside the formal window, and all 11 accepted steps were associated and integrated with zero unassociated steps. The final denied state was approximately `E = 8.108 m, N = -1.311 m`, with 8.213 m displacement and 8.25 m nominal integrated path length. The moving retest accepted and matched 30/30 protected-GT fixes, but Android-reported horizontal-accuracy metadata ranged from approximately 17.36 m to 57.12 m. Its approximately 19.99 m median error, 48.24 m p95 error, and 19.78 m final pre-correction error therefore validate the Evaluation Mode and firewall data flow, not Config A navigation accuracy or survey-grade position error. Protected-GNSS accuracy remains **NOT VALIDATED**. The successful physical results reported every estimator-access/use firewall flag false, `gnssCorrectionApplied = false`, and `firewallMutationSelfTestPassed = true`; explicit `evaluation_cancelled` cancellation passed. No raw GNSS coordinates, ground-truth or denied trajectory, timestamps, or device identifier are returned or persisted.

Stage 7 — Quality Engine + EKF Sensor Fusion is implemented as Config D profile `config_d_navguard_ekf_v1`, statically validated across six implementation/test paths, and physically verified for its defined diagnostic scope. Config A remains baseline PDR, Config B improved heading, Config C ARCore relative motion, and Config D quality-aware PDR + heading + ARCore EKF fusion. The three-state horizontal model is `[E, N, heading]` in `local_enu`; heading is clockwise from true North, normalized to `[0, 2π)`, with circular innovation in `(-π, π]`. PDR remains step-driven with the fixed, uncalibrated, unvalidated 0.75 m assumption and no accelerometer integration. Heading uses a provisional 15-degree measurement sigma; ARCore uses `Frame.getAndroidSensorPose()` with the Stage 5 transform and a provisional 0.35 m position sigma. Joseph-form covariance updates and covariance symmetry are implemented, but no physical calibration is claimed.

The exact quality states are `UNKNOWN`, `GOOD`, `USABLE`, `DEGRADED`, `UNRELIABLE`, and `UNAVAILABLE`. `GOOD`, `USABLE`, and `DEGRADED` apply covariance multipliers 1, 2, and 6; the other states skip the relevant EKF update. Heading and step events use `SensorEvent.timestamp`. `Frame.getTimestamp()` is limited to AR duplicate, monotonicity, and rate diagnostics; AR fusion ordering uses `SystemClock.elapsedRealtimeNanos()` captured after a usable frame update. Unsupported cross-clock comparison is disabled, and equal fusion timestamps resolve in `heading,step,arcore` order. Each run captures for 30 seconds and then replays deterministically without returning a trajectory.

Static validation passed with `flutter analyze --no-pub`, all 191/191 tests, `flutter build apk --debug --no-pub`, and `git diff --check`. Physical verification on the Xiaomi Redmi Note 9 Pro running Android 12 / API 31 passed for stationary, straight-walk, turn/L-shaped, and cancellation scenarios. Final fused horizontal displacement was approximately 0.0179 m stationary, 12.5051 m on the straight walk, and 10.0186 m on the turn/L-shaped walk. These are session observations, not accuracy claims. The AR-degradation attempt remained in tracking (`GOOD` 895, `USABLE` 2, zero `DEGRADED`/`UNRELIABLE`/`UNAVAILABLE`) and therefore passed with observation: fallback logic is implemented and statically tested, but physical AR-loss fallback is **NOT VALIDATED**. Explicit cancellation returned `navguard_fusion_cancelled`.

Protected pre-denial GNSS anchor data is used only for declination. Stage 7 does not access protected ground truth, request live GNSS, apply GNSS correction, return raw trajectory/timestamps, or persist raw sensor, ARCore, camera, or anchor-coordinate data. Config D Quality Engine + EKF fusion remains implemented for its defined scope, while fusion accuracy, quality thresholds, noise parameters, step/step-length/heading/true-north/ARCore accuracy, and physical AR-loss fallback remain **NOT VALIDATED**.

Stage 8 — GNSS Denial / Recovery + Full NAVGUARD Flow is implemented, statically validated, and physically verified for its defined runtime scope. The successful state sequence is `ACQUIRING_GNSS → NORMAL_GNSS → DENIED_NAVGUARD → RECOVERY_PENDING → RECOVERED_GNSS → COMPLETED`, with `IDLE`, `CANCELLED`, and `FAILED` also represented. Denial is software-defined: no RF interference or spoofing is used. The physical `GPS_PROVIDER` listener may remain active, but every GNSS fix generated during `DENIED_NAVGUARD` is quarantined before estimator, heading, PDR, Quality Engine, or controller access. Mutation invariance passed and protected ground truth is not accessed.

Operational GNSS uses `Location.getElapsedRealtimeNanos`; operation boundaries use `SystemClock.elapsedRealtimeNanos`. Initial acquisition and post-gate recovery each require three consecutive acceptable fresh fixes under the frozen 50 m engineering threshold, whose accuracy is not validated. At denial entry, the latest accepted normal-GNSS local ENU becomes the horizontal origin and the EKF begins at `[E_denial_origin, N_denial_origin, latest true heading]`, not ENU zero. Config D retains `[E,N,heading]`, step-driven PDR, true-north rotation-vector heading, ARCore relative ENU, the Quality Engine, Joseph covariance updates, and circular heading innovation. `Frame.getTimestamp()` is not used for cross-source ordering; AR fusion ordering uses `SystemClock.elapsedRealtimeNanos()`. GNSS bearing is never used.

Static validation passed with `flutter analyze --no-pub`, 211/211 tests, `flutter build apk --debug --no-pub`, and `git diff --check`. The stationary full-flow session completed with 1,532 heading updates, zero PDR predictions, 897 ARCore updates, zero denied-GNSS estimator uses, and approximately 0.007818 m pre-recovery displacement. The first walking test exposed a real integration bug: 13 accepted step opportunities were skipped for no heading despite 1,532 valid headings. Stage 8 had retained only the latest delivered heading, so a delayed step could see only a future heading while its older causal heading had been discarded.

The fix buffers heading and step histories and deterministically replays events by timestamp, with equal timestamps ordered `HEADING → STEP → ARCORE_POSITION`; every step selects the greatest heading satisfying `T_heading <= T_step`, and future headings remain prohibited. Delayed-step, multiple-step, equal-timestamp, future-only, representative approximately 1,500-heading, and counter-invariant regressions passed. In the targeted walking retest, all 16 accepted step opportunities became 16 PDR predictions with zero no-heading and zero quality skips; 1,533 heading and 899 ARCore measurements were applied, and final denied qualities were `USABLE / USABLE / GOOD / GOOD`. This is a targeted physical bugfix pass, not step-detection or navigation-accuracy validation.

Recovery-gate counters now have one scope: `recoveryAcceptedFixCount + recoveryRejectedFixCount = recoveryCandidateFixCount`. The retest reported `3 + 1 = 4`; the following recovered observation separately reported five accepted and zero rejected fixes. The approximately 73.46 m recovery correction is the distance between the pre-recovery denied estimate and operational recovered GNSS position, not true error or estimator accuracy. Cancellation returned `full_navguard_flow_cancelled`. Raw GNSS coordinates/fixes, sensor samples, ARCore poses, trajectories, timestamps, and camera images are not returned or persisted. Overall NAVGUARD physical verification remains **PARTIAL**, the device baseline is **NOT FROZEN**, and full-flow, GNSS-recovery, fusion, quality-threshold, noise-parameter, step, heading, true-north, and ARCore accuracy remain **NOT VALIDATED**. Stage 9 — Experiments + A/B/C/D Benchmark + Final UI / Documentation / Demo is next and is **NOT IMPLEMENTED**.

Aşama 7 — Quality Engine + EKF Sensör Füzyonu, Yapılandırma D profili `config_d_navguard_ekf_v1` olarak uygulandı, altı uygulama/test yolu kapsamında statik olarak doğrulandı ve tanımlı tanı kapsamında fiziksel olarak doğrulandı. Yapılandırma A baseline PDR, Yapılandırma B geliştirilmiş heading, Yapılandırma C ARCore göreli hareket ve Yapılandırma D kalite-duyarlı PDR + heading + ARCore EKF füzyonu olarak kalır. Üç durumlu yatay model `local_enu` içinde `[E, N, heading]` biçimindedir; heading gerçek Kuzeyden saat yönünde pozitiftir, `[0, 2π)` aralığına normalize edilir ve dairesel innovation `(-π, π]` aralığındadır. PDR adım tabanlıdır; sabit, kalibre edilmemiş ve doğrulanmamış 0,75 m varsayımını kullanır ve ivmeölçer entegrasyonu yapmaz. Heading için geçici 15 derecelik measurement sigma; ARCore için `Frame.getAndroidSensorPose()`, Stage 5 dönüşümü ve geçici 0,35 m konum sigma'sı kullanılır. Joseph-form kovaryans güncellemesi ve kovaryans simetrisi uygulanmıştır; fiziksel kalibrasyon iddia edilmez.

Kesin kalite durumları `UNKNOWN`, `GOOD`, `USABLE`, `DEGRADED`, `UNRELIABLE` ve `UNAVAILABLE` değerleridir. `GOOD`, `USABLE` ve `DEGRADED` sırasıyla 1, 2 ve 6 kovaryans çarpanı uygular; diğer durumlar ilgili EKF güncellemesini atlar. Heading ve adım olayları `SensorEvent.timestamp` kullanır. `Frame.getTimestamp()` yalnızca AR duplicate, monotoniklik ve hız tanılarıyla sınırlıdır; AR füzyon sıralaması kullanılabilir kare güncellemesinden sonra alınan `SystemClock.elapsedRealtimeNanos()` değerini kullanır. Desteklenmeyen cross-clock karşılaştırması kapalıdır; eşit füzyon zaman damgaları `heading,step,arcore` sırasıyla çözülür. Her çalışma 30 saniye capture yapar, ardından rota döndürmeden deterministik replay uygular.

Statik doğrulama `flutter analyze --no-pub`, 191/191 testin tamamı, `flutter build apk --debug --no-pub` ve `git diff --check` ile geçti. Nihai fused yatay yer değiştirme sabit oturumda yaklaşık 0,0179 m, düz yürüyüşte 12,5051 m ve dönüş/L-biçimli yürüyüşte 10,0186 m idi. Bunlar oturum gözlemleridir, doğruluk iddiası değildir. AR bozulma denemesi tracking durumunda kaldı (`GOOD` 895, `USABLE` 2, sıfır `DEGRADED`/`UNRELIABLE`/`UNAVAILABLE`); bu nedenle gözlemle geçti: fallback mantığı uygulandı ve statik olarak test edildi ancak fiziksel AR-kaybı fallback'i **DOĞRULANMAMIŞTIR**. Açık iptal `navguard_fusion_cancelled` döndürdü.

Kesinti öncesi korumalı GNSS anchor verisi yalnızca declination için kullanılır. Stage 7 korumalı ground truth'a erişmez, canlı GNSS istemez, GNSS düzeltmesi uygulamaz, ham rota/zaman damgası döndürmez ve ham sensör, ARCore, kamera veya anchor-koordinat verisini kalıcılaştırmaz. Aşama 8 — GNSS Kesintisi / Geri Kazanım + Tam NAVGUARD Akışı uygulandı, statik olarak doğrulandı ve tanımlı çalışma zamanı kapsamında fiziksel olarak doğrulandı. Başarılı durum dizisi `ACQUIRING_GNSS → NORMAL_GNSS → DENIED_NAVGUARD → RECOVERY_PENDING → RECOVERED_GNSS → COMPLETED` biçimindedir; `IDLE`, `CANCELLED` ve `FAILED` da temsil edilir. Kesinti yazılım-tanımlıdır; RF paraziti veya spoofing kullanılmaz. Fiziksel `GPS_PROVIDER` dinleyicisi etkin kalabilir ancak `DENIED_NAVGUARD` sırasında üretilen her GNSS fix'i tahmin motoru, heading, PDR, Quality Engine veya denetleyici erişiminden önce karantinaya alınır. Operasyonel GNSS `Location.getElapsedRealtimeNanos`, operasyon sınırları `SystemClock.elapsedRealtimeNanos` kullanır. İlk edinim ve gate-sonrası recovery, doğruluğu doğrulanmamış sabit 50 m mühendislik eşiği altında art arda üç kabul edilebilir taze fix gerektirir. Kesinti girişinde son kabul edilen normal-GNSS yerel ENU, yatay kesinti başlangıcı olur ve EKF ENU sıfırdan değil `[E_kesinti_başlangıcı, N_kesinti_başlangıcı, son gerçek heading]` durumundan başlar. Yapılandırma D; `[E,N,heading]`, adım tabanlı PDR, gerçek-kuzey rotation-vector heading, ARCore göreli ENU, Quality Engine, Joseph kovaryans güncellemeleri ve dairesel heading innovation kullanmayı sürdürür. `Frame.getTimestamp()` cross-source sıralamada kullanılmaz; AR füzyon sıralaması `SystemClock.elapsedRealtimeNanos()` kullanır. İlk yürüyüş testi gerçek bir entegrasyon hatası açığa çıkardı: 1.532 geçerli heading'e rağmen kabul edilen 13 adım fırsatı heading-yok nedeniyle atlandı. Stage 8 yalnızca en son teslim edilen heading'i tuttuğundan gecikmiş bir adım yalnızca gelecekteki heading'i görebiliyor, eski nedensel heading ise kayboluyordu.

Düzeltme heading ve adım geçmişlerini tamponlar ve olayları zaman damgasına göre deterministik replay eder; eşit zaman damgalarında sıra `HEADING → STEP → ARCORE_POSITION` biçimindedir. Gecikmiş-adım, çoklu-adım, eşit-zaman-damgası, yalnızca-gelecek, yaklaşık 1.500-heading temsilî akış ve sayaç değişmezi regresyonları geçti.
